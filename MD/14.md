OMEGA MD/418 — REV22 Kernel Qualification Closure
0. Definiciones
KERNEL_UNDER_TEST
= implementación concreta, hash-bound, sometida a T0.0.4.

kernel_origin ∈ {
  RETAINED_CODE,
  REBUILT_FOR_T0
}

SOURCE_SET
= conjunto exacto de fuentes, headers y archivos de build
  enumerados en el manifiesto del kernel.

REPRO_BUILD
= build limpia realizada exclusivamente desde SOURCE_SET,
  con toolchain, entorno y flags congelados.

Q4_CANONICAL_LAYOUT
= representación byte-a-byte normativa definida por MD/417.

KERNEL_EXEC_LAYOUT
= representación interna persistente opcional derivada
  losslessly de Q4_CANONICAL_LAYOUT.

B_core_actual
= totalidad de bytes persistentes dependientes de los pesos
  que permanecen vivos mientras el núcleo está cargado.
I. AMB-68 — KERNEL REBUILT_FOR_T0
1. AMB-68(a) — ACEPTAR

Se conserva el nombre normativo:

RETAINED_KERNEL_MANIFEST.json

aunque para esta campaña:

kernel_origin = REBUILT_FOR_T0
Responsable de creación

El JUEZ genera el manifiesto mediante inventario read-only del candidato ya seleccionado.

No modifica fuentes ni build durante ese inventario.

El manifiesto debe contener como mínimo:

kernel_origin
source files + SHA-256
headers propios relevantes + SHA-256
build files + SHA-256
compiler/toolchain exacto
compiler version
compiler/linker flags
ISA targets
runner/harness
encoder_entry_points
output binaries + SHA-256
SOURCE_SET aggregate hash
Auditoría

Debe auditarlo una instancia independiente del autor del kernel.

El auditor verifica, al menos:

existencia de cada archivo/símbolo
hashes
SOURCE_SET
flags
toolchain
encoder_entry_points
kernel_origin
correspondencia fuente → build

AMB-68(a) CLOSED.

2. AMB-68(b) — ACEPTAR CON REQUISITOS COMPLETOS

build reproducible significa:

2.1 Dos builds independientes

Realizar:

BUILD_A
BUILD_B

desde directorios limpios y distintos.

Ambas parten únicamente de:

mismo SOURCE_SET
mismo toolchain
misma versión
mismos flags
mismo entorno congelado

No se reutilizan:

.obj
.pch
.lib generados
cache de build
salidas intermedias del otro build
2.2 Criterio gobernante

Para cada binario contractual:

SHA256(binary_A) = SHA256(binary_B)

Debe ser igualdad de bytes exactos.

2.3 MSVC

Si se usa MSVC, congelar flags necesarios para determinismo, incluyendo cuando proceda:

/Brepro
/INCREMENTAL:NO

y cualquier opción adicional necesaria para eliminar timestamps/IDs no deterministas.

No se acepta como sustituto:

"misma funcionalidad"
"mismo código desensamblado"
"solo cambia timestamp"

si los SHA difieren.

2.4 Fallo

Si las dos builds no producen hashes idénticos:

REPRO_BUILD = FAIL
KERNEL_UNDER_TEST = NOT_FROZEN
NO_LAUNCH

No constituye fallo de OMEGA ni del kernel matemático; es fallo de calificación del artefacto.

AMB-68(b) CLOSED.

3. AMB-68(c) — ACEPTAR

Los nombres normativos existentes se conservan.

Para esta campaña, referencias históricas como:

RETAINED_KERNEL_NOT_QUALIFIED
NOT_FOUND
NOT_BUILDABLE

se interpretan sobre el KERNEL_UNDER_TEST aplicable en ese momento.

Cuando:

kernel_origin = REBUILT_FOR_T0

y el candidato falla:

kernel_rebuild_required = true

significa:

producir una nueva versión del kernel, con nuevo SOURCE_SET/hash/binario, y someterla desde cero a la calificación completa.

Está prohibido:

repetir exactamente el mismo binario
bajo un nuevo run_id para intentar obtener PASS.

II. AMB-69 — CUANTIZACIÓN DE ACTIVACIONES
4. AMB-69(a) — ACEPTAR CON expected_error_class

La cuantización Q8 de activaciones forma parte del operador contractual de todas las rutas:

AVX2
AVX-VNNI

Por tanto un fixture que pruebe un error contractual de activaciones aplica a toda ruta aplicable.

4.1 Manifest

Añadir:

expected_error_class ∈ {
  NONE,
  ENCODER_RANGE_ERROR,
  ACTIVATION_RANGE_ERROR
}

a kernel_cases_manifest.json.

No inferir la clase únicamente desde fixture_class.

4.2 Clasificación
STANDARD
→ expected_error_class = NONE

STRESS_IN_DOMAIN
→ expected_error_class = NONE

STRESS_EXPECTED_REJECT
→ expected_error_class ∈ {
    ENCODER_RANGE_ERROR,
    ACTIVATION_RANGE_ERROR
  }
4.3 ACTIVATION_RANGE_ERROR

Para un fixture etiquetado:

STRESS_EXPECTED_REJECT
expected_error_class = ACTIVATION_RANGE_ERROR

el preflight debe comprobar:

1. cuantizador escalar → ACTIVATION_RANGE_ERROR
2. segunda ejecución escalar → ACTIVATION_RANGE_ERROR
3. referencia PyTorch independiente → misma clasificación

sin producir una salida numérica válida para ese operador.

Durante 5.4, cada ruta aplicable del kernel debe:

devolver ACTIVATION_RANGE_ERROR
no emitir output parcial tratado como válido
4.4 Dominio binary32

Confirmo:

overflow de a_scale = imposible

para entradas finite binary32, porque:

max_float32 / 127 < max_float32.

El caso contractual relevante es el redondeo de una escala positiva a:

+0.0f

por underflow para activaciones suficientemente diminutas.

AMB-69(a) CLOSED.

5. AMB-69(b) — ACEPTAR

Las dos referencias independientes deben emular el mismo operador contractual completo:

binary32 input
→ quantización Q8 por grupo
→ q_a
→ a_scale_fp32
→ Q4 weights
→ integer dot
→ rescaling/acumulación contractual

Antes de comparar referencias debe verificarse bit-exactamente:

q_a_scalar = q_a_torch
a_scale_fp32_scalar bits = a_scale_fp32_torch bits

para los casos aceptados.

Después se aplican:

max_abs_ref <= 1e-9
nRMS_ref    <= 1e-10

a los outputs de referencia.

Q4_FORMAT.md continúa siendo el nivel textual normativo; las dos implementaciones son referencias ejecutables independientes.

AMB-69 CLOSED.

III. AMB-70 — KERNEL_EXEC_LAYOUT
6. AMB-70(a) — ACEPTAR CON PRECISIÓN

Para cada conjunto de pesos contractual de los fixtures:

Q4_CANONICAL_LAYOUT
→ kernel pack/repack
→ KERNEL_EXEC_LAYOUT
→ canonical unpack

El resultado desempaquetado debe satisfacer:

SHA256(canonical_unpacked)
=
SHA256(canonical_original)

sobre todos los bytes canónicos, incluidos:

payload Q4
scales FP16
orden de grupos
orden de matrices

La metadata/padding propios de KERNEL_EXEC_LAYOUT no forman parte del SHA canónico porque no pertenecen al layout canónico.

El resultado se registra en:

T0_0_4_kernel_qualification.json

por fixture.

Si cualquier round-trip falla:

KERNEL_EXEC_LAYOUT_ROUNDTRIP = FAIL
→ paso correspondiente de 5.4 = FAIL
→ RETAINED_KERNEL_NOT_QUALIFIED

No se permite seguir a perf como si fuera sólo una anomalía de serialización.

AMB-70(a) CLOSED.

7. AMB-70(b) — ACEPTAR

B_core_actual incluye todo byte persistente cuya existencia dependa de los pesos y que permanezca vivo durante la residencia normal del núcleo:

Q4 payload
weight scales
padding
alignment overhead
repacked weight copies
weight-derived lookup tables
persistent permutation/index metadata
persistent row/group offsets
cualquier metadata necesaria para interpretar los pesos

Si se mantienen simultáneamente:

canonical copy
+
repacked execution copy

ambas cuentan en B_core_actual.

Se excluyen:

activaciones
q_a temporales
activation scales temporales
accumulators
scratch
temporary conversion buffers
outputs
instrumentation
code pages
tooling

Regla general:

si el byte debe permanecer asignado para que los pesos
permanezcan cargados y utilizables,
cuenta en B_core_actual.

AMB-70 CLOSED.

VI. RACIONAL
Reproducibilidad

T0.0 necesita identificar un binario concreto. Si dos builds desde exactamente las mismas entradas producen bytes diferentes, todavía no existe una identidad de kernel suficientemente cerrada para una campaña física rigurosa.

Error de activaciones

fixture_class indica el tipo general del caso; expected_error_class especifica qué contrato de rechazo se está probando. Son dimensiones distintas y no deben inferirse ambiguamente.

Layout interno

OMEGA puede optimizar libremente la representación nativa, pero esa libertad termina donde cambia q o scale. El round-trip al layout canónico convierte esa regla en una prueba mecánica.

B_core_actual

Para una tesis de residencia física importa la huella persistente real, no sólo el payload matemático ideal.
