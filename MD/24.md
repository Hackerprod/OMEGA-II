SOL — T0.0 Kernel Adequacy and Peak Definition
1. Definiciones
P_instr(r,c)
= techo medido de MAC/s de la primitiva aritmética de la ruta ISA r
  en el tipo de core c, con operandos residentes en registros y sin
  decode Q4, escalas, loads de pesos ni reducción externa.

P_Q4(r,c,m)
= MAC/s del operador Q4 completo y correcto para la ruta r,
  tipo de core c y matrixización m, con el working set de pesos
  residente en caché.

P_Q4_peak(r,c)
= max_m P_Q4(r,c,m).

eta_instr(r,c,m)
= P_Q4(r,c,m) / P_instr(r,c).

eta_Q4(r,c,m)
= P_Q4(r,c,m) / P_Q4_peak(r,c).

q_eff
= 18/32 = 0.5625 bytes persistentes Q4 por peso/MAC en m=1.

BW_Q4_8P(m=1)
= demanda lógica agregada de pesos del operador Q4 completo
  ejecutado en los 8 P-cores a m=1.

BW_D(8)
= ancho de banda DRAM sostenido ya medido con 8 workers físicos.

D_mem
= BW_Q4_8P(m=1) / BW_D(8).
2. T0.0-e — DECISIÓN
Se miden y reportan AMBOS picos

ACEPTO la opción (c).

T0.0-e queda separado en dos cantidades distintas.

2.1 Techo de instrucción

Medir:

P_instr(AVX2,P)
P_instr(AVX-VNNI,P)

y, como caracterización T0.0:
P_instr(AVX2,E)
P_instr(AVX-VNNI,E)

El microbenchmark debe:

usar exactamente la semántica integer-dot de la ruta real;
mantener operandos en registros;
eliminar decode Q4;
eliminar conversión de escalas;
eliminar tráfico de pesos;
evitar dependencia serial artificial salvo la necesaria
para mantener acumuladores correctos;
usar varios acumuladores independientes suficientes
para medir throughput y no latencia.

Para el operador actual:

AVX2
→ primitiva equivalente a la aritmética signed-word usada por el kernel.

AVX-VNNI
→ VPDPWSSD de 256 bits o la primitiva exacta usada por la ruta.

No mezclar una microprimitiva con semántica distinta únicamente porque tenga mayor throughput teórico.

P_instr es el techo de hardware/ISA.

No es el denominador de eta_Q4.

2.2 Pico del operador Q4 completo

Medir el operador completo sobre un barrido T0.0 de:

m ∈ {1,2,4,8,16,32}

con pesos residentes.

Entonces:

P_Q4_peak(r,c)
= máximo medido sobre ese barrido.

Este es el pico operativo Q4.

Por tanto:

0 <= eta_Q4(m) <= 1

por construcción.

La medición actual:

~1.134e9 MAC/s P AVX2
~1.133e9 MAC/s P VNNI

deja de llamarse «pico».

Se conserva y se reclasifica como:

P_Q4(r,P,m=1) baseline pre-optimization.

No se descarta ningún dato original.

3. Significado de las dos eficiencias

Reportar ambas:

eta_instr
= qué fracción del techo aritmético de ISA consigue el operador real.

eta_Q4
= dónde se encuentra cada m respecto del mejor régimen del
  operador completo.

No utilizar una para sustituir a la otra.

En particular, el antiguo problema:

eta(m) > 1

desaparece porque el denominador de eta_Q4 ya no es m=1, sino el máximo residente observado sobre el barrido congelado.

4. Kernel actual — NO es todavía adecuado para H0

La observación del JUEZ es correcta.

Con:

P_Q4(m=1) ≈ 1.13e9 MAC/s/P-core

q_eff = 0.5625 B/MAC

la demanda lógica de pesos es aproximadamente:

~0.64 GB/s/P-core.

Con ocho P-cores esto es del orden de:

~5 GB/s agregados,

muy por debajo de:

BW_D(8) = 67.3 GB/s.

Un H0 A-vs-B ejecutado ahora tendría alto riesgo de medir:

compute/decode overhead

en lugar del mecanismo de residencia que pretende falsar.

Por tanto:

CURRENT_Q4_KERNEL
= ENGINEERING_BASELINE
= NOT_H0_READY

Esto no es un fallo de OMEGA.

5. Optimización antes de T0.1 — OBLIGATORIA
DECISIÓN

Sí. Se exige una fase acotada de optimización del kernel antes de autorizar T0.1/H0.

Su único objetivo es eliminar el riesgo de que H0 sea no discriminante por un kernel artificialmente lento.

Permitido optimizar, entre otros:

decode/dequant fusionado;
conversión FP16→FP32 fuera del inner loop cuando sea reutilizable;
eliminación de binary64 innecesario del hot path si correctness
permanece bit-exact respecto del contrato;
acumuladores vectoriales en registros;
unrolling;
reducción de branches/indexing;
repacking/alignment;
reutilización apropiada de escalas;
matrixización m.

Condición absoluta:

correctness existente debe seguir PASS.

No se autoriza cambiar el operador matemático para ganar velocidad.

6. Criterio cuantitativo de adecuación para H0

No usaré como gate principal una fracción arbitraria de P_instr, porque Q4 incluye trabajo real que el microbenchmark de instrucción deliberadamente elimina.

El criterio debe estar ligado al mecanismo que H0 necesita observar.

Definir:

D_mem
= BW_Q4_8P(m=1) / BW_D(8).

donde:

BW_Q4_8P(m=1)
= suma sobre los 8 P-cores de
  [P_Q4(core,m=1) × 0.5625 B/MAC].
Gate mínimo

Antes de T0.1:

D_mem >= 0.50

debe cumplirse para al menos una de las rutas contractuales correctas:

AVX2
o
AVX-VNNI.

Con el BW_D(8) actualmente medido:

BW_D(8) = 67.3 GB/s

el umbral equivale aproximadamente a:

BW_Q4_8P(m=1) >= 33.65 GB/s

o, si los ocho P-cores están razonablemente balanceados:

~4.21 GB/s/P-core
~7.48e9 MAC/s/P-core.

Esto es aproximadamente 6.6× el throughput m=1 actual.

El valor exacto gobernante se calcula desde las mediciones, no desde este redondeo explicativo.

7. Uso de eta_instr

eta_instr se reporta obligatoriamente, pero no es gate independiente.

Sirve para diagnosticar:

decode-bound
scale-conversion-bound
reduction-bound
instruction-throughput-bound

Si D_mem pasa aunque eta_instr sea modesto, el kernel es suficientemente agresivo para que H0 pueda someter a prueba el mecanismo de memoria.

Si D_mem no pasa:

T0.1 = HOLD
reason = KERNEL_MEMORY_PRESSURE_INADEQUATE

No ejecutar H0 esperando que la variante B revele una diferencia que el kernel no tiene capacidad de demandar.

8. Alcance de la optimización

La optimización puede usar únicamente:

resident Q4 kernel benchmarks;
P_instr;
P_Q4(m);
correctness;
profiling del propio hot loop.

Está prohibido durante esta fase usar para tuning:

A/B/C de H0;
K copias residentes/no residentes;
resultado de rho;
buffer de expulsión;
ningún gate H0.

Así se evita optimizar retrospectivamente contra el experimento que debe seguir siendo falsable.

9. Número de ciclos

Autorizar:

ONE_BOUNDED_KERNEL_OPTIMIZATION_PHASE

No significa un solo commit.

Puede contener varias modificaciones internas y perfiles hasta producir un candidato final.

Una vez declarado candidato final:

freeze código/binario;
correctness completa;
repetir las mediciones T0.0 afectadas;
evaluar D_mem.

Si no alcanza:

D_mem >= 0.50

no iniciar una segunda campaña automáticamente.

Resultado:

KERNEL_MEMORY_PRESSURE_INADEQUATE
T0.1 = HOLD

y volver a Sol con perfil y resultados.

Tras congelar el kernel optimizado:

Repetir
T0.0-d

T0.0-e
completo:
  P_instr
  P_Q4(m)
  P_Q4_peak
  eta_instr
  eta_Q4;

T0.0-f:
  BW_L2,i derivado del kernel;
  BW_L2,Sigma / demanda lógica del kernel;
  cualquier fila A/B/C descriptiva de T0.0 que dependa
  directamente del throughput del kernel.
No es necesario repetir
BW_D(n) memcpy

si:

hardware
power plan
worker affinity
background conditions

no cambiaron materialmente.

El BW_D(n) actual permanece como caracterización de plataforma.

11. AVX2 vs AVX-VNNI

Después de la optimización:

correctness PASS para ambas
→ medir ambas.

No asumir que VNNI debe ganar.

La ruta para T0.1 se selecciona por rendimiento observado y estabilidad.

Si permanecen indistinguibles dentro del ruido experimental:

usar AVX2 como tie-break determinista

por ser la baseline ISA ya contractual.

Esto no declara VNNI inferior; sólo evita una selección arbitraria cuando no hay evidencia de ventaja.
