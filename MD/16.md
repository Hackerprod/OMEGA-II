I. CONTRATO DE SALIDA
1. Ruling (1) — ACEPTAR CON PRECISIÓN

La salida contractual del operador es:

y_out = binary32_RNE(y_acc64)

donde:

y_acc64

se obtiene acumulando en binary64 las contribuciones de grupos en orden estrictamente ascendente de g.

La conversión final usa:

IEEE-754 round-to-nearest, ties-to-even.
1.1 Dominio de fixtures

Para todo fixture que pretenda ser:

STANDARD
o
STRESS_IN_DOMAIN

el preflight debe demostrar, usando las referencias independientes:

y_acc64 es finito

AND

abs(y_acc64) <= FLT_MAX

para cada elemento de salida.

Si no se cumple:

preflight_status = FIXTURE_SET_INVALID
NO_LAUNCH

No se crea una nueva clase de error runtime para overflow de salida.

El harness simplemente no presenta como STRESS_IN_DOMAIN un vector cuyo resultado contractual no sea representable dentro del dominio congelado.

1.2 Finitud del kernel

Para un fixture aceptado por el preflight:

y_out debe ser finito.

Un Inf o NaN producido por el kernel en ese dominio es:

kernel correctness FAIL

no una extensión válida del contrato.

1.3 Tolerancias

Las tolerancias existentes se comparan contra el operador completo:

binary32 inputs
→ Q8 activations
→ Q4 weights
→ integer dots
→ binary64 rescaling/accumulation
→ final binary32 RNE.

La referencia usada para juzgar el output debe incluir también esa conversión final a binary32 antes de efectuar la comparación kernel-vs-reference.

RULING 1 ACCEPTED_WITH_PRECISION.

II. ACTIVACIONES FINITAS
2. Ruling (2) — ACEPTAR

Toda activación contractual debe ser:

IEEE binary32
AND finite.

Quedan fuera del dominio:

NaN
+Inf
-Inf

El preflight debe rechazarlas como fixture inválido:

FIXTURE_SET_INVALID
NO_LAUNCH

El KERNEL_UNDER_TEST no está obligado a definir ni detectar comportamiento para activaciones no finitas, porque el harness oficial no puede suministrarlas.

Esto no impide añadir pruebas defensivas QA_ONLY, pero tales pruebas:

EVIDENTIARY_WEIGHT = ZERO

y no amplían el contrato.

RULING 2 ACCEPTED.

III. BYTES Q4 CANÓNICOS INVÁLIDOS
3. Ruling (3) — ACEPTAR CON INVARIANTES CANÓNICAS COMPLETAS

El kernel oficial puede asumir que todo buffer Q4 recibido ha pasado validación canónica previa.

Un grupo es CANONICAL_Q4_VALID sólo si:

cada nibble decodifica q ∈ [-7,+7]

scale es IEEE binary16 finito

signbit(scale) = 0

Por tanto:

nibble 0x8
→ INVALID_CANONICAL_Q4

scale NaN
→ INVALID_CANONICAL_Q4

scale +Inf/-Inf
→ INVALID_CANONICAL_Q4

scale negativo
→ INVALID_CANONICAL_Q4

scale = -0
→ INVALID_CANONICAL_Q4

Añadir además la invariante derivada del encoder:

si scale == +0
→ todos los q del grupo deben ser 0.

Un grupo con:

scale=+0
y algún q!=0

también está fuera del dominio canónico, aunque una decodificación puramente aritmética pudiera producir ceros.

3.1 Responsabilidad

El encoder de referencia nunca produce bytes inválidos.

El preflight verifica las invariantes anteriores para todos los pesos oficiales.

El kernel no está obligado a revalidarlas en cada llamada.

Si el harness entrega bytes no canónicos durante una corrida oficial:

harness/input defect
≠ kernel defect

y no puede utilizarse para adjudicar el kernel.

RULING 3 ACCEPTED_WITH_PRECISION.

IV. RUTA SCALAR EMBEBIDA
4. Ruling (4) — ELEGIR ELIMINACIÓN DEL KERNEL FINAL

La ruta scalar de autocontrol debe eliminarse o compilarse fuera del KERNEL_UNDER_TEST final.

El binario congelado para T0.0 debe exponer como KERNEL_CONTRACT_ROUTE únicamente:

AVX2
AVX-VNNI

cuando AVX-VNNI esté disponible en el target.

La referencia scalar independiente ya proporciona el oráculo requerido.

Puede existir código scalar para:

QA_ONLY
unit tests
reference tooling
development diagnostics

pero no debe quedar como una ruta seleccionable/ejecutable dentro del binario contractual congelado.

Así:

"todas las rutas presentes"

no genera una tercera ruta accidental que tenga que entrar en la adjudicación.

RULING 4 = REMOVE_SCALAR_FROM_FINAL_KUT.

V. POLÍTICA DE FORMAS
5. Ruling (5) — ACEPTAR DOMINIO GENÉRICO, NO WHITELIST DE SIETE FORMAS

No se impone una lista cerrada de las siete matrices como limitación de la primitiva.

Definir:

O = número de outputs / filas de pesos
I = dimensión de entrada
M = número de filas de activación procesadas conjuntamente

El SUPPORTED_SHAPE_DOMAIN es:

O > 0
M > 0
I > 0
I mod 32 = 0

y el tamaño canónico exacto de pesos debe ser:

W_bytes_expected
= O * (I/32) * 18.

La comprobación de esta aritmética debe ser:

overflow-safe

antes de comparar tamaños.

Una llamada es inválida si:

O <= 0
M <= 0
I <= 0
I mod 32 != 0
W_bytes != W_bytes_expected
o la aritmética necesaria desborda el tipo de tamaño.

Debe rechazarse explícitamente mediante el mecanismo determinista del kernel.

5.1 Formas oficiales

kernel_cases_manifest.json enumera las:

OFFICIAL_FIXTURE_SHAPE

que realmente participan en la calificación T0.0.

Las formas contractuales d512 deben estar representadas allí según REV23/REV24.

5.2 Formas QA/stress adicionales

Formas menores u otras formas dentro de SUPPORTED_SHAPE_DOMAIN pueden utilizarse como:

QA_SHAPE

o stress engineering.

Eso no amplía por sí solo la evidencia científica más allá de las formas declaradas oficialmente.

5.3 Significado de “exactamente las dimensiones esperadas”

En 5.4.5 debe interpretarse mecánicamente como:

la llamada cumple SUPPORTED_SHAPE_DOMAIN
+
el tamaño de pesos y demás dimensiones contractuales
son internamente consistentes.

No significa:

"la API sólo acepta exactamente siete tuplas codificadas."

RULING 5 ACCEPTED_WITH_PRECISION.

VI. NOTAS INFORMATIVAS DE Q4_FORMAT.md
6. Ruling (6) — AUTORIZAR CON REDACCIÓN PRECISA

Pueden incluirse bajo un encabezado literal:

INFORMATIVO — SIN AUTORIDAD NORMATIVA ADICIONAL
6.1 Scale FP16

Puede documentarse:

Las comprobaciones de rango se aplican a scale_exact64
ANTES de convertir a binary16.

Por tanto:

scale_exact64 > 65504
→ ENCODER_RANGE_ERROR

aunque algún valor apenas superior a 65504 pudiera redondear a un valor finito bajo otra política.

Asimismo:

0 < scale_exact64 < 2^-24
→ ENCODER_RANGE_ERROR

antes del redondeo.

No limitar la nota sólo al subintervalo [2^-25,2^-24); la regla normativa cubre todo (0,2^-24).

6.2 Cero negativo en pesos

Puede documentarse:

abs(-0.0) = +0.0
→ max_abs = 0 cuando todos los pesos son ±0
→ scale = +0
→ todos q = 0.

La codificación canónica usa +0, nunca -0.

6.3 Frontera de ACTIVATION_RANGE_ERROR

Para:

a_max64

procedente de activaciones finite binary32 positivas, puede documentarse:

ACTIVATION_RANGE_ERROR
iff
0 < a_max64 <= 63 * 2^-149.

Y:

a_max64 = 64 * 2^-149

es aceptado porque:

a_max64 / 127

queda por encima del punto medio hacia el menor subnormal binary32 positivo y redondea a un a_scale_fp32 no cero.

Estas notas son consecuencias matemáticas; si alguna vez contradijeran el cuerpo normativo, gobierna el cuerpo normativo.

RULING 6 AUTHORIZED_AS_INFORMATIONAL.

IX. RACIONAL
9.1 Salida

La referencia float64 puede ser finita mientras una conversión binary32 no lo sea. El contrato debe separar explícitamente acumulación y representación observable.

9.2 Bytes canónicos

“No obligar al kernel a detectar entradas imposibles” es razonable sólo si el preflight define mecánicamente qué significa imposible/no canónico. La invariante scale=0 → q=0 evita representaciones múltiples de un mismo grupo cero.

9.3 Scalar

Una ruta auxiliar dentro del mismo binario crea una obligación de calificación innecesaria. La referencia independiente es una frontera más limpia.

9.4 Formas

La primitiva puede ser genérica sin convertir cada dimensión aceptada en evidencia T0. El manifest decide qué formas son oficiales; el dominio decide qué llamadas son válidas.
