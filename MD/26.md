1. Definiciones
y_ref
= salida de la referencia escalar que conserva acumulación binary64
  y realiza cast final a binary32.

y_avx2
= salida binary32 de la ruta AVX2 optimizada.

y_vnni
= salida binary32 de la ruta AVX-VNNI-256 optimizada.

G
= I/32 grupos Q4 por fila de pesos.

m_tile
= número de filas de activación que reutilizan un decode de pesos
  dentro del kernel m>1.

TEAM_MAC_RATE_8P
= MAC totales ejecutados simultáneamente por los 8 P-cores
  divididos por un único intervalo de pared del equipo.

BW_Q4_logical_8P
= TEAM_MAC_RATE_8P × 0.5625 B/MAC.

BW_DRAM_read_8P
= bytes realmente solicitados por el benchmark streaming read-only
  de los 8 P-cores divididos por el intervalo de pared del equipo.

D_read
= BW_Q4_logical_8P / BW_DRAM_read_8P.

TIMED_REGION_MIN
= duración mínima aceptable de una muestra cronometrada.
2. Acumulación FP32
DECISIÓN: RATIFICADA PARA T0.0

No exijo conservar acumulación binary64 en el hot path.

La acumulación vectorial FP32 queda autorizada porque T0.0 intenta medir un kernel nativo razonable, no fijar todavía la aritmética definitiva de una red entrenada.

El contrato de correctness del kernel T0 pasa a ser:

1. group_dot entero:
   EXACTO respecto de ISA_REF.

2. outputs:
   todos finitos.

3. para cada elemento:
   |y_kernel - y_ref|
   <= 1e-5 + 1e-5 * |y_ref|.

4. AVX2 y AVX-VNNI:
   los group_dot deben ser idénticos bit a bit.

5. AVX2 y AVX-VNNI:
   sus outputs binary32 deben ser bit a bit idénticos
   para el mismo fixture.

El punto 5 es razonable porque, una vez demostrado que ambas rutas producen exactamente los mismos int32 dot, el camino FP32 posterior es el mismo.

Si una ruta pasa la tolerancia contra y_ref pero AVX2 y VNNI dejan de ser bit-identical:

CORRECTNESS = HOLD

hasta explicar la divergencia.

No se acepta simplemente ampliar tolerancias.

2.1 Alcance

Esta decisión vale para:

T0 physical/kernel qualification

y no fija automáticamente la política numérica de T1–T4.

Por tanto la frase previa de MD/24:

"eliminar binary64 si correctness permanece bit-exact"

queda refinada a:

integer path = bit-exact
output FP32 = bounded-error contract anterior.

4. BLOQUEANTE 1 — ruta m>1 repite el decode de pesos

El código descrito hace:

for o
    for mBase step 2
        execute_output_block(...)
            for g
                decode_q4_group(...)

Por tanto, para una fila de pesos:

m=2  → cada grupo se decodifica 1 vez
m=4  → 2 veces
m=8  → 4 veces
m=16 → 8 veces
m=32 → 16 veces

Eso significa que m>1 no reutiliza los pesos a través de todo M; sólo a través de:

m_tile = 2.

No es un error de correctness, pero sí es relevante para la interpretación de:

P_Q4(m)
P_Q4_peak
eta_Q4(m).

Además el harness actualmente registra:

logicalBytes = payload_bytes * calls

aunque el kernel vuelve a cargar/decodificar el payload aproximadamente:

ceil(M/m_tile)

veces.

DECISIÓN

Antes de la sesión oficial debe hacerse una de estas dos cosas:

Opción A — preferida

Optimizar el kernel m>1 con un m_tile mayor elegido durante la fase de ingeniería previa, sin usar resultados H0.

El tile final queda congelado antes de la sesión oficial.

No impongo m_tile=4 u 8; debe elegirse por implementación/register pressure.

Opción B — permitida

Mantener m_tile=2, pero congelarlo explícitamente y distinguir:

canonical_weight_payload_bytes_per_call
= payload_bytes

kernel_weight_payload_traversals_per_call
= ceil(M/2)

kernel_weight_payload_load_bytes_logical
= payload_bytes * ceil(M/2)

En ningún caso llamar al primer valor «bytes realmente leídos por el kernel» para m>2.

Para:

D_read

esto no afecta porque el gate se calcula exclusivamente en m=1.

Por tanto no obligo a cambiar m_tile=2 para D_read, pero sí obligo a resolver la contabilidad/etiquetado antes de medir P_Q4(m) oficialmente.

5. BLOQUEANTE 2 — 128 llamadas pueden hacer muestras demasiado cortas

El valor:

KERNEL_CALLS_PER_SAMPLE = 128

era razonable con el kernel de ~1.1e9 MAC/s.

Con el kernel optimizado puede dejar regiones de sólo unos pocos milisegundos.

Eso aumenta demasiado la sensibilidad a:

scheduler
interrupts
QPC overhead relativo
turbo/transitorios
actividad de fondo.
DECISIÓN

Fijar:

TIMED_REGION_MIN = 100 ms

para:

P_instr
P_Q4(m)
P_Q4_8P_m1
BW_DRAM_read_8P
E-core confirmation.

Antes de las 31 muestras se permite una calibración:

ENGINEERING_CALIBRATION_ONLY

que únicamente determina el número de iteraciones/calls necesario para alcanzar >=100 ms.

Después:

calls/iterations quedan congelados para esa serie.

La calibración:

NO entra en estadísticas
NO permite elegir una ruta
NO permite cambiar umbrales
NO es evidencia T0.

No modificar el número de calls después de observar las 31 muestras.

6. BLOQUEANTE 3 — posible eliminación del loop batch por el compilador

El batch ejecuta repetidamente:

execute_core(..., same inputs, same output pointer)

y cada iteración sobrescribe el mismo output.

__declspec(noinline) en el batch por sí solo no demuestra que el compilador mantuvo las 128 ejecuciones completas.

Antes de medir debe existir una comprobación de binario que demuestre:

el loop calls existe;
el core se ejecuta calls veces;
la aritmética no fue hoisted fuera del loop;
las iteraciones anteriores no fueron eliminadas como dead computation.

Puede satisfacerse mediante:

disassembly inspection
+
QA que contraste calls=1 vs calls=N con un contador/sink
fuera del timer.

No introduzcas escrituras diagnósticas por iteración dentro del hot path sólo para impedir optimización.

Si es necesario, usar una barrera de compilador o una frontera noinline apropiada.

10. BW_DRAM_read_8P

El benchmark read-only debe cumplir antes de usarse para D_read:

8 P-cores físicos;
SMT siblings no usados;
buffer independiente por worker;
buffer pre-touched fuera del timer;
working set por worker > LLC;
sin page faults dentro del timer;
sequential read;

Los bytes contabilizados son:

no lectura+escritura como en el antiguo memcpy.

12. Pregunta 4 — D_read
DECISIÓN: MEDICIÓN SIMULTÁNEA DE 8 P-CORES

No usar:

suma de las ocho mediciones single-core.

El numerador debe provenir de una ejecución concurrente real:

8 threads
→ uno por P-core físico
→ SMT sibling no utilizado
→ barrera común
→ misma ruta ISA
→ m=1
→ mismo intervalo de equipo.

Entonces:

TEAM_MAC_RATE_8P
= Σ MAC ejecutados por los 8 workers
  / team_wall_time.

Y:

BW_Q4_logical_8P
= TEAM_MAC_RATE_8P × 0.5625.

El denominador:

BW_DRAM_read_8P

se mide igualmente con los mismos 8 P-cores físicos simultáneamente.

Así:

D_read
= concurrent logical Q4 weight demand
  /
  concurrent DRAM read capability.

Ésta es la única comparación coherente con el gate.

13. Medición de equipo

Para las series 8P, usar un intervalo de pared de equipo.

Preferencia:

todos los workers preparados
→ barrier
→ coordinator registra QPC_start
→ release
→ todos ejecutan trabajo fijo
→ join/barrier completion
→ QPC_end.

Alternativamente puede usarse:

min(worker_start)
→ max(worker_end)

si queda demostrado que representa la misma ventana.

No sumar medianas o tiempos single-core para construir artificialmente el throughput 8P.
