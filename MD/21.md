OMEGA MD/425 — PRE-RUN L2 Counter Candidate Selection
0. Definiciones
L2_FILL
= evento simbólico P-core L2_LINES_IN.ALL.

L2_MISS
= evento simbólico P-core L2_REQUEST.MISS
  o alias enumerado L2_RQSTS.MISS.

B_logical
= bytes lógicos conocidos que el benchmark exige leer.

CL_bytes
= tamaño de línea de caché verificado por la plataforma.

R_L2
= observable causal normalizado requerido por REV25
  para detectar la transición L2.

L2_PRIMARY_CANDIDATE
= candidato preferido para construir R_L2.

L2_SECONDARY_CANDIDATE
= candidato de corroboración causal.

EVENT_DB_LABEL
= texto literal que la herramienta reporta sobre la
  base de eventos utilizada; no es una inferencia de
  microarquitectura.
I. SELECCIÓN DEL OBSERVABLE L2
1. Congelar AMBOS candidatos

DECISIÓN: congelar ambos eventos como INSTRUMENTATION_CANDIDATE, con funciones distintas.

L2_PRIMARY_CANDIDATE
= L2_LINES_IN.ALL

L2_SECONDARY_CANDIDATE
= L2_REQUEST.MISS / L2_RQSTS.MISS

No declarar ninguno VALID durante PRE-RUN.

Intel describe L2_LINES_IN.ALL como contador de líneas que llenan L2, mientras L2_RQSTS.MISS cuenta requests de lectura que producen un true miss en L2. Son observables relacionados pero no idénticos.

2. Razón para usar L2_LINES_IN.ALL como primario

REV25 necesita finalmente un observable normalizable a bytes.

L2_LINES_IN.ALL cuenta unidades explícitamente descritas como:

cache lines filling L2

por lo que, después de verificar CL_bytes en la plataforma:

R_L2_fill
= L2_FILL_count * CL_bytes / B_logical

tiene una conversión dimensional directa.

Esto no presupone antes del run que el evento sea causalmente adecuado.

Su uso oficial requiere que T0.0.2 demuestre el criterio de CounterMove y el control small-vs-large congelado.

Si no pasa:

L2_FILL = INVALID

y no puede gobernar C_L2.

II. L2_REQUEST.MISS
3. Mantenerlo como candidato secundario

L2_REQUEST.MISS es semánticamente muy útil porque representa requests que realmente fallaron L2; Intel documenta el evento P-core correspondiente como true misses y excluye misses fusionados con uno ya pendiente.

Debe congelarse como:

L2_SECONDARY_CANDIDATE

y recopilarse, si la herramienta permite hacerlo sin invalidar/multiplexar la ventana.

Su papel es:

corroborar la transición causal;
detectar inconsistencias del fill counter;
servir como fallback sólo si puede normalizarse
mecánicamente conforme a REV25.

No autorizo convertir automáticamente:

L2_REQUEST.MISS * 64

a bytes únicamente porque el evento se llame MISS.

Para que L2_MISS sustituya al primario como fuente formal de R_L2, T0.0.2 debe demostrar que la semántica/documentación de la ruta congelada permite interpretar cada evento como una transferencia de una línea completa o proporcionar otra conversión documentada y verificable.

No inventar esa equivalencia.

III. AUSENCIA DE RAW EVENT ID
4. Un ID numérico NO es requisito por sí mismo

La ausencia de EventSel/UMask numéricos en la enumeración local no bloquea el freeze del candidato si se cumplen todos estos puntos:

1. herramienta exacta congelada;

2. selector explícito P-core;

3. nombre simbólico exacto;

4. descripción textual enumerada localmente;

5. comando exacto que produjo la enumeración;

6. stdout/stderr raw hash-bound;

7. la herramienta puede seleccionar el evento
   inequívocamente por ese nombre simbólico.

Por tanto son aceptables como candidatos:

P-core / L2_LINES_IN.ALL
P-core / L2_REQUEST.MISS

sin inventar un raw ID.

Si al configurar la colección oficial el nombre resulta ambiguo, se resuelve a otro evento, o la herramienta exige un raw ID que no puede establecerse documentalmente:

candidate = NOT_ESTABLISHED

y no se lanza una inferencia manual.

IV. EMON Database: alderlake
5. Confirmación

Sí: registrar literalmente

EVENT_DB_LABEL = "alderlake"

es procedencia válida de lo que VTune/SEP reportó.

Debe acompañarse de algo equivalente a:

event_db_label_source
= "sep -platform-info"

event_db_label_semantics
= TOOL_REPORTED_LITERAL

event_db_mapping_inference
= NONE

No significa:

CPU 0xB7 == Alder Lake

ni modifica la identidad ya congelada:

GenuineIntel
family 6
model 0xB7 / 183
Raptor Lake

La etiqueta sólo documenta qué DB declaró usar la herramienta.

No veo conflicto en conservar simultáneamente:

cpu_uarch = Raptor Lake
tool_reported_event_db = alderlake

porque son campos de naturaleza diferente.

V. DISCREPANCIA DE ALIAS
6. L2_REQUEST.MISS vs L2_RQSTS.MISS

Como la enumeración informa un alias, congelar ambos textos:

canonical_tool_name
alias_name

sin normalizarlos silenciosamente.

El candidato representa una única selección sólo si SEP/VTune confirma que el alias resuelve al mismo evento.

Si produce dos eventos distinguibles:

tratar como dos candidatos diferentes

hasta resolverlo.

VI. INSTRUMENTATION_SELECTION_FREEZE
7. Campos mínimos para L2

Registrar para cada candidato:

core_type = P-core
symbolic_name
alias, si existe
local_description
tool
tool_version/build
driver/version
selection command
raw enumeration log SHA-256
EVENT_DB_LABEL
raw_event_id = NOT_EMITTED
pre_run_status = CANDIDATE

Para L2_FILL añadir:

unit = cache_line
byte_conversion = CL_bytes * event_count
CL_bytes_source = platform verification

pero:

causal_status = NOT_YET_VALIDATED

hasta T0.0.2.

VII. RACIONAL

L2_LINES_IN.ALL y L2_REQUEST.MISS no son intercambiables por nombre.

El primero facilita la normalización dimensional exigida por R_L2; el segundo está más cerca de la semántica de “request que abandona L2 por miss”. Tener ambos congelados permite que la prueba causal oficial determine si el fill counter sigue fielmente la rodilla y, al mismo tiempo, disponer de una corroboración de misses sin adaptar eventos después de ver el resultado.

Esto conserva la separación fundamental:

PRE-RUN:
seleccionar por semántica/documentación

T0.0.2:
validar por comportamiento causal
