1. Definiciones
MAC
= una multiplicación-acumulación escalar.

P_instr(r,c)
= throughput MAC/s de la primitiva aritmética pura de la ruta ISA r
  en tipo de core c, sin decode Q4, conversiones de escala ni tráfico
  de pesos.

P_Q4_1(r,c)
= throughput MAC/s del operador Q4 completo a m=1.

BW_Q4_logical_8P
= P_Q4_1 agregado medido realmente con 8 P-cores
  × 0.5625 B/MAC.

BW_DRAM_read_8P
= throughput de lectura secuencial solamente, con working set claramente
  mayor que LLC, medido con 8 P-cores.

D_read
= BW_Q4_logical_8P / BW_DRAM_read_8P.

HOT_PATH_CLEAN
= kernel cronometrado sin validación invariante, asignaciones,
  estructuras diagnósticas ni escrituras intermedias no requeridas
  por el output contractual.
2. Veredicto sobre MD/24

La conclusión principal de MD/24 se mantiene:

OPTIMIZAR_KERNEL_ANTES_DE_H0 = SÍ

pero modifico el gate cuantitativo.

La regla anterior:

D_mem >= 0.50

como gate único queda:

SUPERSEDED

a la luz del código real.

El problema del kernel actual es más severo y más específico de lo que podía determinarse sólo con los resultados agregados.

3. Pregunta 1 — origen de los ~1.12e9 MAC/s
DECISIÓN: sí, está dominado por implementación

Con el código completo, considero muy alta la evidencia de que:

~1.12e9 MAC/s

no representa un límite aritmético del i7-13700F.

Por cada grupo de 32 MACs se ejecutan aproximadamente:

32 iteraciones escalares para unpack de pesos;
32 conversiones escalares int8→int16 de activaciones;

AVX2:
  2 x vpmaddwd
  2 x vpaddd;

VNNI:
  2 x vpdpwssd;

1 store de vector a stack;
8 lanes reducidos escalarmente;
1 half_to_float;
conversión de escala a double;
multiplicación double;
acumulación double;
store de group_dot.

La diferencia aritmética entre AVX2 y VNNI es una fracción pequeña del trabajo total.

Por eso:

AVX2 ≈ VNNI

es exactamente lo esperable de este hot path y no evidencia que VNNI carezca de ventaja hardware.

3.1 Evidencia cuantitativa del código

Para O=512, I=512, m=1:

MAC/call = 512 × 512 = 262,144

groups/call
= 512 × (512/32)
= 8,192

Por llamada el código realiza:

262,144 iteraciones de unpack de nibble;
262,144 ensanchamientos escalares de activación;
8,192 reducciones horizontales;
8,192 half_to_float;
8,192 actualizaciones binary64;

para sólo:

16,384 instrucciones vector-dot VNNI

o su secuencia AVX2 equivalente.

El perfil estructural es claramente:

SCALAR_OVERHEAD_BOUND

antes que DOT_INSTRUCTION_BOUND.

4. Otros defectos de diseño encontrados
4.1 group_dot no debe existir en el hot path oficial

Actualmente:

M × O × G
= 1 × 512 × 16
= 8,192 int32
= 32 KiB escritos por llamada.

Esto es diagnóstico, no output contractual final.

Para H0:

group_dot materialization = PROHIBIDA_EN_HOT_PATH

Puede existir en una build de correctness/QA, pero no en la build cronometrada.

4.2 accumulator como vector persistente también distorsiona

A m=1:

512 doubles = 4 KiB

pero el source realiza:

8,192 actualizaciones

sobre él por llamada.

Si el compilador no consigue mantener esos valores en registros/locales por la estructura y aliasing, se generan cargas/stores adicionales importantes.

El kernel cronometrado debe acumular localmente y escribir solamente el resultado contractual final.

4.3 resize/assign dentro de cada llamada

Aunque resize() no realoque cuando existe capacidad suficiente:

result.group_dot.resize(...)
result.output.resize(...)
result.accumulator.assign(...)

no pertenecen al hot path que H0 debe medir.

Requisito:

buffers preasignados antes del timer.

Ninguna asignación dinámica debe ser posible dentro de la región medida.

4.4 validate() dentro de la región

Si execute_into_prechecked() todavía termina ejecutando:

validate(w,a)

entonces el nombre prechecked no refleja la ruta medida.

La validación:

formas
sizes
isfinite(a.scale)

debe ejecutarse antes del timer.

El kernel timed puede asumir inputs ya validados.

4.5 half_to_float() por grupo

Una conversión implementada mediante ldexp por cada grupo es especialmente sospechosa.

Debe inspeccionarse el ensamblado final.

Si produce llamada/helper o una secuencia escalar larga:

MAJOR_HOT_PATH_DEFECT

La optimización puede usar una conversión hardware soportada o una representación preparada, siempre que cualquier estado persistente adicional se contabilice correctamente.

4.6 Reducción horizontal por grupo

Este patrón:

vector accumulator
→ store a stack
→ loop escalar de 8 lanes

ocurre 8,192 veces por llamada.

Es un defecto importante.

La reducción debe amortizarse, idealmente manteniendo acumuladores vectoriales a través de múltiples grupos y reduciendo mucho menos frecuentemente.

4.7 Dispatch ISA dentro del inner loop

Actualmente:

route==Scalar ? ...
route==AVX2   ? ...
              : VNNI

se evalúa dentro de cada grupo.

Las rutas oficiales deben tener entry points especializados:

execute_avx2(...)
execute_vnni(...)

o especialización compile-time equivalente.

No hacer dispatch por grupo.

4.8 Layout de activaciones para m>1

El orden:

for(o)
  for(g)
    for(m)

es correcto para reutilizar el peso desempaquetado entre m, pero las activaciones:

a.q + m*I + g*32

quedan separadas por I.

No lo declaro defecto contractual, pero el kernel optimizado puede necesitar layout/repack específico para matrixización.

Cualquier repack persistente o temporal debe contabilizarse adecuadamente.

5. Error importante del harness para el futuro barrido de m

Actualmente:

macs = 2 * O * I * calls

corregido posteriormente por factor 2.

Para m=1 el resultado derivado actual es correcto.

Pero para cualquier futuro:

m > 1

la cuenta correcta de MAC convencionales es:

MACs = M × O × I × calls.

Si el harness conserva la expresión actual durante el barrido:

m ∈ {1,2,4,8,16,32}

subestimará throughput exactamente por factor M.

Esto debe corregirse antes de medir P_Q4(m).

6. BW_L2 actual está mal nombrado

La cantidad calculada como:

payload_Q4_bytes / wall_time

no es ancho de banda físico L2.

Debe renombrarse:

BW_Q4_logical

o:

Q4_WEIGHT_DEMAND_RATE

Lo mismo aplica a:

BW_L2,Sigma

actual.

Los valores:

0.63 GB/s/P
4.90 GB/s 8P

son tasas lógicas de consumo de payload Q4.

No demuestran que esos bytes hayan atravesado L2 a esa tasa.

Por tanto los actuales:

r_A
r_B
r_C

son ratios descriptivos de demanda lógica / memcpy lógico, no medidas de presión física sobre L2/DRAM.

No deben usarse como evidencia H0.

7. BW_D actual también necesita nombre preciso

El harness cuenta:

2 × buffer_size

por memcpy:

lectura lógica + escritura lógica.

Esto es una medida válida de throughput de plataforma, pero debe llamarse:

BW_memcpy_logical(n)

y no tratarse como el techo exacto de un workload read-only.

Además existen pequeños accesos adicionales:

source[...] ^= ...
sink ^= dest[...]

no incluidos en la contabilidad.

Son despreciables frente a 120 MiB, pero confirman que la cifra no es un contador físico de DRAM.

Los datos actuales se conservan.

8. Pregunta 2 — nuevo gate cuantitativo
DECISIÓN: retirar D_mem >= 0.50 como único gate

No fijo una eta_instr mínima arbitraria.

Tampoco acepto únicamente un límite de bytes escritos.

El readiness para H0 tendrá dos componentes:

A. HOT_PATH_CLEAN
B. D_read >= 1.00
8.1 Gate estructural obligatorio

Antes de H0:

HOT_PATH_CLEAN = PASS

requiere al menos:

sin allocation/resize/assign en región cronometrada;
sin validate() invariante dentro del timer;
sin group_dot en hot path;
sin accumulator persistente diagnóstico;
sólo output contractual final como escritura obligatoria;
dispatch ISA fuera del inner loop.

El output contractual permitido es:

M × O × sizeof(float)

más un sink/checksum mínimo fuera del kernel si el harness lo necesita.

No fijo un ratio arbitrario de bytes: elimino directamente las escrituras que no pertenecen al operador.

9. Nuevo gate de presión de memoria

La comparación correcta no debe usar BW_memcpy_logical.

T0.0 debe añadir una medición:

BW_DRAM_read_8P

con:

8 P-cores;
working set claramente > LLC;
streaming load-only;
varios acumuladores/sinks para evitar dependencia serial;
sin gran stream de stores;
misma política estadística N=31/warmup congelada.

Luego medir realmente el kernel optimizado residente con 8 P-cores:

BW_Q4_logical_8P
= MAC/s_8P(m=1) × 0.5625.

Y definir:

D_read
= BW_Q4_logical_8P / BW_DRAM_read_8P.

Gate mínimo:

D_read >= 1.00

antes de autorizar H0.

Interpretación:

D_read < 1

significa que incluso la demanda lógica del kernel residente es menor que la capacidad de lectura DRAM medida; un H0 de residencia tendría alto riesgo de seguir siendo compute/decode-bound.

1.00 es un mínimo de competencia, no el umbral final de efecto H0.

Cuando se resuelvan las AMB de T0.1, el gate H0 puede exigir más headroom según el efecto que H0 pretenda detectar.

10. eta_instr

Debe medirse y reportarse:

eta_instr(m)
= P_Q4(m) / P_instr

pero:

ETA_INSTR_MIN = NONE

por ahora.

Su función es diagnóstica.

Si:

D_read >= 1

con correctness y hot path limpios, no mataré H0 sólo porque Q4 represente una fracción modesta del microbenchmark ideal.

Si D_read < 1, eta_instr ayudará a localizar qué overhead continúa dominando.

11. Microbenchmark P_instr

Debe representar exactamente las primitivas reales.

Para AVX2 no medir sólo vpmaddwd si el kernel necesita:

vpmaddwd + vpaddd

para acumular.

Para VNNI medir:

vpdpwssd

con suficientes acumuladores independientes para medir throughput y no una cadena de latencia.

Así:

P_instr_AVX2
P_instr_VNNI

son techos comparables del operador integer-dot realmente utilizado.

12. Medición de frecuencia efectiva

No usaría una cadena de sumas dependientes suponiendo:

1 iteración = 1 ciclo

como medición absoluta de frecuencia.

Eso mezcla:

latencia de instrucción
loop overhead
front-end
branching
frecuencia

Si VTune/SEP expone:

CPU_CLK_UNHALTED
APERF/MPERF
o métrica equivalente documentada

usar eso.

Si no existe una fuente confiable:

EFFECTIVE_FREQUENCY = UNAVAILABLE

y reportar throughput en MAC/s.

No es necesario conocer GHz exactos para decidir el gate D_read.

13. Pregunta 3 — dos poblaciones de E-cores
DECISIÓN: caracterización T0.0, con una comprobación obligatoria

No colapsar todavía los ocho E-cores a una única cifra.

La separación:

~0.739e9
vs
~0.675e9 MAC/s

es aproximadamente un 9% y, dado el IQR pequeño de varios cores, parece reproducible.

Además no coincide limpiamente con:

cluster E16-19
cluster E20-23.

Por tanto antes de cerrar T0.0 se requiere una comprobación acotada:

1. repetir single-core en los 8 E-cores;
2. orden de cores randomizado;
3. misma afinidad;
4. N=31;
5. ejecutar también P_instr por E-core.

Después:

Si el split aparece también en P_instr

registrar:

E_CORE_THROUGHPUT_HETEROGENEITY = MEASURED

y conservar datos por core.

No es fallo de T0.0.

Si P_instr es homogéneo pero Q4 mantiene el split

investigar:

interrupciones/background;
mapping lógico;
cache/cluster;
hot-path interaction.

antes de utilizar una media E global.

Esto sigue siendo caracterización T0.0; la selección de políticas P/E continúa perteneciendo a T0.1 según la decisión anterior.

15. Optimización autorizada

El kernel final debe apuntar a eliminar específicamente los defectos observados.

Prioridades:

1. eliminar group_dot hot-path;
2. preasignar outputs;
3. eliminar validate del timer;
4. vectorizar int8→int16;
5. vectorizar/reducir unpack Q4;
6. reducir horizontalmente con mucha menor frecuencia;
7. eliminar ldexp/half conversion costosa del inner loop;
8. mantener acumuladores en registros/locales;
9. separar entry points AVX2/VNNI;
10. explotar reutilización de pesos para m>1.

No es obligatorio implementar exactamente cada técnica si el resultado final pasa los gates.

Correctness sigue siendo innegociable.
